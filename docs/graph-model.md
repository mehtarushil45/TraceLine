# Graph Construction Layer

This document describes TraceLine's graph construction layer, which turns the
enriched payment network (`data/processed/payment_network/`) into two
complementary representations.

## 1. Heterogeneous evidence graph

Built by `src.graph.builder.build_evidence_graph`. A typed property graph
(`EvidenceGraph`) preserving node types, relationship types, and attributes.

### Node types (`NodeType`)

| Type | Source | Attributes preserved |
| --- | --- | --- |
| `Account` | `accounts.csv` | customer_name, balance, risk_score, creation_date |
| `Merchant` | `merchants.csv` | name, category, country, risk_tier |
| `Device` | `devices.csv` | os, device_type, first_seen |
| `PaymentInstrument` | `payment_instruments.csv` | instrument_type, network, last4, expiry |
| `IP` | `ip_addresses.csv` | isp, country, is_mobile_isp |
| `Transaction` | `enriched_transactions.csv` | timestamp, amount, payment_method, transaction_status |

### Edge types (`EdgeType`)

| Edge | From -> To | Attributes |
| --- | --- | --- |
| `USES_DEVICE` | Account -> Device | - |
| `USES_INSTRUMENT` | Account -> PaymentInstrument | - |
| `USES_IP` | Account -> IP | - |
| `FROM_ACCOUNT` | Transaction -> Account (sender) | timestamp |
| `TO_ACCOUNT` | Transaction -> Account (receiver) | timestamp |
| `AT_MERCHANT` | Transaction -> Merchant | timestamp |

## 2. Account relationship graph

Built by `src.graph.projection.project_account_graph`. Nodes are accounts;
two accounts are connected when they share observable entities or show a
relevant temporal/merchant relationship. Each undirected edge carries the
full evidence behind it:

```
shared_devices       : sorted tuple of shared device ids
shared_instruments   : sorted tuple of shared instrument ids
shared_ips           : sorted tuple of shared IP addresses
shared_merchants     : sorted tuple of merchants both accounts touched
temporal_overlap     : number of calendar days both accounts had transactions
weight               : float score (see below)
```

### Weight model

Base weights per evidence kind (strongest to weakest), defined in
`EVIDENCE_BASE_WEIGHTS`:

| Evidence kind | Base weight |
| --- | --- |
| Shared payment instrument | **4.0** (strongest) |
| Shared device | **3.0** (strong) |
| Shared merchant (via transactions) | **2.0** (moderate) |
| Shared IP | **1.0** (weak) |

Additional entities of the same kind contribute with diminishing returns
(square-root scaling). The final weight is::

    weight = sum_t w_t * sqrt(count_t) * temporal_multiplier

with the temporal multiplier::

    temporal_multiplier = min(1 + 0.25 * temporal_overlap, 2.0)

(1.0 when the accounts never transact on a shared day.) The scoring lives in
the pure function `evidence_weight(...)`, so weights are unit-testable.

## Label-leakage prevention

* The transaction loader reads an explicit whitelist of **observable columns**
  only; `pattern_id` and `is_ring_member` are never loaded.
* The `link_type` column of the relationship files is also not imported,
  since its values derive from enrichment internals.
* No projection input or output contains evaluation labels; a test rebuilds
  both graphs from label-stripped copies of the data and requires identical
  canonical serializations.

Known artifact: in the current synthetic data some device ids embed ring
naming (e.g. `dev_ring_pat_0`) because they were generated by the enrichment
layer as ordinary observable ids. Graph construction treats all ids opaquely;
downstream feature engineering must do the same and must not parse id
prefixes.

## Determinism & complexity

* All iteration that influences output runs over sorted ids; both graphs
  expose deterministic canonical JSON serializations (`to_canonical()`).
* Pair discovery uses inverted indexes (entity -> accounts) with compact
  memory-bounded accumulators.
* **Temporal merchant co-occurrence**: Merchant sharing is indexed by
  `(merchant_id, calendar_date)`. This captures coordinated same-day bursts
  without materializing unconstrained $O(N^2)$ global merchant cliques across
  the full multi-month simulation.
* Transactions are streamed in chunks with an optional row `--limit`.

## Usage

```bash
# Build both graphs over the processed data and print summaries:
python -m src.graph.builder --top 10

# Dev fast path: load only the first N transactions:
python -m src.graph.builder --limit 2000
```

```python
from pathlib import Path
from src.graph.builder import build_evidence_graph
from src.graph.projection import project_account_graph

g = build_evidence_graph(Path("data/processed/payment_network"), limit=2000)
ag = project_account_graph(g)
df = ag.to_dataframe()   # edges with evidence + weights, sorted
```

## Tests

```bash
python -m pytest tests/test_graph.py -v
```

Covers: typed nodes exist, crafted shared entities create relationships,
evidence-strength weight ordering plus the temporal multiplier, evaluation
labels never entering construction, and deterministic output.

Deliberately out of scope here: community detection (Louvain), ML scoring,
and any serving layer.
